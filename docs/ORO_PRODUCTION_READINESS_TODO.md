# Oro production readiness TODO

The work that takes Oro from its state on 2026-10-23 (branch `1.0`, commit `cf8eab3`) to a messaging service I can run
for personal users and Umoja's business customers. Every task comes from reading the code, the schema and the
deployment files, and from checks against the local stack. Paths are relative to `Repositories/`:

- `oro/backend`: the Oro backend (the path `Repositories/Asata` does not exist)
- `1_ASATA_DATABASE`: the schema (`CREATE_ORO_TABLES.sql`) and the seed (`oro/INSERT.sql`)
- `umoja`: Umoja, the first product using Oro

Estimates are for one developer, in developer-days (1 d = 6 to 7 focused hours), implementation and its tests
together unless split. Companion documents: [launch checklist](ORO_LAUNCH_CHECKLIST.md),
[technical debt](ORO_TECHNICAL_DEBT.md).

## Executive summary

### Two launches, not one

- **Umoja launch**: business messaging inside organizations. Umoja already authenticates its users, so Oro's own
  accounts are not needed.
- **Oro launch**: the standalone app for everyday users. It needs everything above plus accounts, abuse controls
  (blocking, reporting, who may message whom) and most likely push notifications.

### What I checked and how

| Check | Result |
|---|---|
| The API login `oro_service` takes `oro_system` (rolled-back transaction) | It can: `oro_system` reads the messages of both products |
| A plain member, as `oro_app`, promotes itself, removes the owner, renames the group (rolled back) | The database allowed all three |
| `PUT /oro/internal/...` through Umoja's public frontend (port 4201) | It reaches Oro: Oro answered 401 |
| SQL built by concatenation | Constants only, no injection found |
| Path traversal in the local storage | Keys generated by Oro and checked again under the root |
| Search and members who joined without the history | Covered by `theSearchFindsWhatTheMemberMayReadOnly` |
| Context leaking to the next user of a pooled connection | Covered by `theContextDoesNotLeakToTheNextTransactionOfAPooledConnection` |
| Umoja refresh tokens | Opaque and hashed: they cannot be used as Oro tokens |

### Confirmed defects

1. `ORO-SEC-001`: the API login can switch to `oro_system`, which bypasses every product and membership rule.
2. `ORO-SEC-002`: roles and member removal are enforced by the Java code only; the database lets any member do it.
3. `ORO-SEC-003`: Oro holds Umoja's token signing secret, so a compromise of Oro lets anyone mint Umoja tokens,
   admin roles included.
4. `ORO-SEC-005`: `/oro/internal` is reachable from the internet through Umoja's nginx.
5. `ORO-SEC-007`: an open stream keeps receiving events and presence after its token expired, the identity was
   suspended or the organization access was revoked (up to 30 minutes).
6. `ORO-SEC-008`: two synchronizations of one organization can interleave, and an older snapshot committed last
   gives back an access that was just revoked.
7. `ORO-SEC-010`, `011`, `012`: no rate limit, no stream limit, no storage quota.
8. `ORO-SEC-013`: in Oro, anyone can open a direct conversation with, or add to a group, any user.
9. `ORO-LCH-006`: files of deleted messages are never deleted (the purge job does not exist).
10. `ORO-SCL-004`: one slow stream client blocks the outbox worker for every user.

### Unverified risks

- `ORO-SEC-009`: database error details (failing row values, possibly message text) may reach the logs.
- `ORO-SEC-020`: JDBC queries outside Hibernate have no timeout.
- `ORO-LCH-012`: graceful shutdown with 30-minute streams.
- Behaviour under load: nothing has been measured (`ORO-SCL-007`).

### The five most important tasks

1. `ORO-SEC-001`: separate database logins for the API and for the system work.
2. `ORO-SEC-003`: asymmetric token signing, so that Oro can verify Umoja tokens without being able to sign them.
3. `ORO-SEC-007`: re-authorize or close open streams.
4. `ORO-LCH-007`: backups with point-in-time recovery, and one restore actually done.
5. `ORO-SEC-010`: rate limits and quotas on the public API.

### Critical dependencies

- `ORO-SEC-003` (asymmetric tokens) comes before `ORO-LCH-001` (Oro accounts), so that Oro issues its tokens the
  same way from day one.
- `ORO-SEC-001` (two logins) comes before `ORO-LCH-008` (secrets), which then has two secrets to store.
- `ORO-LCH-009` (versioned migrations) comes before any schema change after launch, including `ORO-SEC-002`.
- `ORO-LCH-010` (metrics) comes before `ORO-SCL-007` (load tests), which need it to read the results.
- `ORO-LCH-003` (object storage) and `ORO-LCH-004` (scanner) both come before turning on files in production.

- [x] `ORO-SEC-003` — P0 — Stop sharing Umoja's signing secret: asymmetric tokens with an audience
  - Done (2026-10-23): Umoja signs RS256 with its own RSA key (`config/security/JwtKeys.java`), names it by thumbprint and publishes the public keys on `/umoja/.well-known/jwks.json`; its tokens carry `aud: [umoja, oro]`. Oro reads them from `UMOJA_JWKS_URI`, accepts RS256 only and the audience `oro`, and holds no Umoja secret. No transition flag: the refresh tokens are opaque, so a client gets one 401 and a new RS256 token. Tested: `ApiTest.aTokenNeedsTheKeyAndTheAudienceOfItsProduct`, `JwkSetUriTest` (rotation without restart), Umoja's `JwtKeysTest` and `AuthApiIntegrationTest`.
  - Current state: Confirmed design risk
  - Evidence: `oro/backend/src/main/resources/application.yml` (`UMOJA_JWT_SECRET`),
    `SecurityConfig.userTokenManagers` (HS256 with the shared secret);
    `umoja/backend/src/main/java/com/asata/org/umoja/auth/service/TokenService.java` signs HS256 tokens carrying
    `roles` and `permissions`. With HMAC, whoever verifies can also sign: a leak of Oro's environment gives Umoja admin
    tokens.
  - Action: Umoja signs with an asymmetric key (ES256 or EdDSA) and publishes its public keys (JWKS with `kid`) on
    an internal URL or as configuration. Add `aud` (`umoja`, `oro`) to its access tokens. Oro verifies with
    `NimbusJwtDecoder.withJwkSetUri` or a static public key, checks the audience, and drops `UMOJA_JWT_SECRET`. Keep
    HS256 accepted for one release behind a flag for the switch.
  - Acceptance criteria: Oro starts without any Umoja secret; a token signed with the old HMAC secret is refused once
    the flag is off; a token without `aud` containing `oro` is refused; key rotation by `kid` works without restarting
    Oro.
  - Dependencies: None (Umoja and Oro change together)
  - Estimate: 2 to 3 d across both repositories
  - Launch impact: Blocker
  - Verification: `ApiTest` with tokens signed by a test key pair: wrong key, wrong audience, unknown `kid`, rotation
