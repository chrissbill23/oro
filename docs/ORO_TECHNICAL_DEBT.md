# Oro technical debt

The choices that limit Oro today, why they were made, what they risk, and when to revisit them. The tasks are in
[the TODO list](ORO_PRODUCTION_READINESS_TODO.md).

## Security architecture

### One process for the API and the workers

- **Today**: two logins and two pools in one process (`context/DataSourceConfig.java`, done on 2026-10-23): the API's
  can never take `oro_system`.
- **Risk**: a flaw that runs code in the process (not just SQL) still reaches the worker's pool.
- **Revisit**: when the workers need to scale apart from the API, or before handling data that needs a stronger
  separation: run them as their own process with only the worker's login.

### The identity of the context is a setting

- **Today**: RLS and the triggers (roles included, since 2026-10-23) read the identity from `oro.identity_id`, which
  `DbSession` sets per transaction.
- **Risk**: any SQL on the API's connection could set another identity; the triggers protect against a bug in the
  services, the separate logins against `oro_system`, but not against an injection acting as another user.
- **Revisit**: if an injection is ever found, or when the API moves to per-request database credentials (not planned).

### Signing keys in the environment

- **Today**: Umoja signs RS256 with its own private key and publishes the public ones; Oro holds no product secret
  (since 2026-10-23). The private key is a variable of Umoja's environment (`UMOJA_JWT_SIGNING_KEY`), and an unset key
  means a new one at each start.
- **Risk**: whoever reads Umoja's environment can sign its tokens; a forgotten key in production makes every restart
  sign everyone out.
- **Revisit**: Oro reads its secrets from files and refuses to start on settings of development (`ORO-LCH-008`, done
  on 2026-10-23), but Umoja does not yet: its key still comes from `backend/.env.local`, and it still starts with a
  new key when none is set. Next: the key as a secret file, a production profile in Umoja that refuses to start
  without it, a scheduled rotation (`UMOJA_JWT_PREVIOUS_KEYS`).

### Integration keys over plain HTTP

- **Today**: named keys per product, kept as SHA-256 hashes, several at once for a rotation (`IntegrationKeyFilter`,
  since 2026-10-23); a change of the list needs a restart of Oro. Umoja sends its key in a header, over plain HTTP on
  the private network.
- **Risk**: whoever can read the traffic of the private network reads the key; a key is a bearer secret, not bound to
  a request.
- **Revisit**: mTLS or signed requests (an HMAC of the request and a timestamp) when Oro and its products run on
  different networks or hosts; reload the list without a restart if rotations become frequent.

## Data model

### Strict per-conversation order under a row lock

- **Today**: each send locks its conversation and takes `last_message_seq + 1`.
- **Why**: order without gaps, stable cursors, unread counts without counting rows, idempotent retries.
- **Risk**: sends in one conversation take turns, a few hundred per second at most. Fine for chat, not for broadcast
  channels with thousands of senders.
- **Revisit**: when lock waits on `oro_conversation` pass 50 ms p99, or when broadcast channels are a product
  requirement (`ORO-SCL-003`).

### Read positions instead of per-message receipts

- **Today**: `last_read_seq` and `last_delivered_seq` per member.
- **Why**: one update per read instead of one row per message and recipient.
- **Risk**: no "seen by 12" lists in groups, no marking one older message as read.
- **Revisit**: when the product asks for read-by-whom in groups. Keep the positions for the counts even then.

### Deletion is a tombstone, and there is no edit history

- **Today**: a deleted message keeps its row and order, its content is erased; edits overwrite the text.
- **Why**: privacy first: what a sender deletes or changes is gone.
- **Risk**: old versions still live in table pages until vacuum, in the WAL and in backups; moderators cannot see
  what was said before an edit. Adding edit history later must not bring back what deletion erased.
- **Revisit**: with the retention policy (`ORO-SEC-014`, `ORO-LCH-018`), before any edit history (`ORO-FEA-003`).

### `metadata` holds mentions only

- **Today** (since 2026-10-24): a message of a user may carry `{"mentions": [...]}`, members of the conversation
  only, checked by the API (`MessageMetadata`); any other key is refused. The database only limits the size: the rule
  is in Java.
- **Why**: clients render what senders wrote; a forged preview or system event would mislead them.
- **Risk**: a new kind of metadata (link previews, replies) needs a change of Oro first; an edit keeps the mentions of
  the first text.
- **Revisit**: with threads and replies (`ORO-FEA-004`), and before any link preview: generated by the server, never
  sent by a client.

### Search by trigrams

- **Today**: `ILIKE '%…%'` over the user's readable messages, 30 results, through `oro_search_messages` (since
  2026-10-24): a function that applies the rule of the policy of the messages itself, because under RLS no index can
  serve `ILIKE`; the trigram index (`idx_oro_message_body_trgm`) then serves it. 2 ms for a typical user, 0.4 to
  0.7 s in a conversation of a million messages (`backend/perf`).
- **Risk**: the rule of who reads which message is written twice, in the policy and in the function: a change of one
  must change the other (`MessagingFeaturesTest.theSearchFollowsTheRuleOfThePolicyOfTheMessages`). No ranking, no
  stemming; the index slows the sends a little.
- **Revisit**: when users ask for relevance or languages (full-text search with a `tsvector`, which also bounds the
  large conversations), or search p95 over 300 ms.

### The list of the conversations is not paged

- **Today**: `GET /conversations` returns every active conversation of the user, with its last message and its count
  of members: about 0.1 ms each at the database (13 ms for 40, 81 ms for 823, `backend/perf`).
- **Risk**: a user in hundreds of conversations pays it on every refresh of the list (Umoja reads it again after
  every change).
- **Revisit**: when users have hundreds of conversations: the newest 50, then more (an API change for the clients).

### No partitioning

- **Today**: `oro_message` is one table.
- **Why**: per-conversation queries use one index; partitioning adds work with no gain at this size.
- **Revisit**: 200 to 500 M rows or 100 to 200 GB, autovacuum falling behind, or a retention policy that drops old
  data in bulk (`ORO-SCL-008`).

## Runtime

### One instance: streams, presence and rate limits in memory

- **Today**: `LiveHub` keeps the streams and who is online in the memory of the instance, and `RateLimiter` the
  buckets of the rate limits (a restart refills them; two instances would each allow the full rate).
- **Why**: no message broker, nothing more to run.
- **Risk**: one instance is a single point of failure; a restart drops every stream (clients reconnect and catch up);
  capacity is bounded by one machine: about 1,000 people active at once with 5,000 connected on 2 CPUs, breaking
  between 1,500 and 2,000 (`backend/perf`, 2026-10-24).
- **Revisit**: when the availability target needs a second instance, CPU passes 60 % at peak, or open streams pass
  ~10k. Use PostgreSQL `LISTEN/NOTIFY` first; Redis only if it is measured to be insufficient (`ORO-SCL-006`).

### A queue and a writer per stream

- **Today** (since 2026-10-24): events are queued per stream (500 at most) and written by a virtual thread of that
  stream; a stream whose queue is full is ended, and its client reconnects and catches up through the API.
- **Risk**: an event sits in memory until it is written: 10,000 streams with full queues hold 5 million references
  (the events themselves are shared, a few hundred bytes each). A blocked write ties up its virtual thread until the
  socket times out.
- **Revisit**: if `oro_streams_ended_slow_total` grows for clients that are not slow (a burst larger than 500 events),
  or with several instances (`ORO-SCL-006`).

### Stream authorization checked every 30 s

- **Today**: a stream ends with its token and closes with the commit of a revocation on this instance
  (`LiveAuthorization`, since 2026-10-23); a change made elsewhere is found by the check every 30 s.
- **Risk**: up to 30 s of events and presence after a change made outside the services.
- **Revisit**: with several instances (`ORO-SCL-006`): the closes must travel with the events.

### The outbox only feeds the streams

- **Today**: the only handler is `LiveOutboxEventHandler`; events retry for up to an hour. Since 2026-10-24 an event
  older than 2 minutes is not sent: its recipients reconnect and read again instead. A `failed` event raises
  `OroOutboxFailed`, and `ops/outbox-replay.sh` puts it back once fixed.
- **Why**: the outbox was built ahead for push and other consumers.
- **Risk**: the time-to-live belongs to the live handler; a second consumer (push) needs its own, and must not lose
  its events to it. A long outage of the outbox reconnects every stream once.
- **Revisit**: with push (`ORO-FEA-001`): a handler per consumer, its own time-to-live, deduplication
  (`ORO-SCL-010`).

### Quotas can be passed by one file

- **Today**: the storage quota of a user counts every file not deleted. The uploads never attached to a message count
  until the purge job removes them after 24 h (`AttachmentPurge`, since 2026-10-23). Two uploads at the same moment
  may both pass the quota.
- **Risk**: a user whose uploads failed may find its quota full for up to a day; a quota overshoot of one file.
- **Revisit**: when users report it.

### Files through the API on a local disk

- **Today**: `LocalFileStorage`; uploads and downloads stream through the API; scanned by clamd; the volume backed up
  by restic, apart from the database (`files-backup`); all since 2026-10-23.
- **Why**: one authorization path, nothing extra to run in development.
- **Risk**: the files and the database are backed up apart, so a restore to a point in time can find a file missing
  or a file with no row (the backend README, Recovering Oro); the files live on one server; API threads are busy with
  large transfers and their scans; a file found clean later is not announced on the streams; ClamAV needs about
  1.5 GB of memory.
- **Revisit**: object storage when a second server is needed or the disk is too small (`ORO-LCH-003`); signed URLs
  only when transfers load the API (measured); an event for a file scanned late if clients need it.

## Operations

### A schema script and a small runner, no migration tool

- **Today**: `CREATE_ORO_TABLES.sql` builds a new database; numbered migrations, run by `oro/migrate.sh` and recorded
  in `oro_schema_version`, change an existing one (since 2026-10-23).
- **Risk**: a change must be written twice (the schema and a migration); one runner at a time, by hand or in a
  deployment step; the products other than Oro still have no versioning.
- **Revisit**: when two people change the schema at once often, or when Mokili and Umoja need the same: a tool
  (Flyway, Liquibase) for the whole database.

### The shared Asata database

- **Today**: Oro's tables live in the `asata` database next to Umoja's, with their own roles and RLS.
- **Why**: one PostgreSQL to run for every Asata service.
- **Risk**: one superuser, one backup and one outage for every product; heavy load from one product slows the
  others; a restore to a point in time rewinds every product.
- **Revisit**: when Oro's load or its recovery needs differ from Umoja's: a separate database first (same
  server), a separate server after.

### CI and monitoring on one server

- **Today** (since 2026-10-23): CI runs the tests and builds the image on every push and pull request, and `main`
  requires it to pass. Oro logs JSON, exposes its metrics on the management port, and Prometheus and Alertmanager run
  next to it with 19 rules.
- **Risk**: the monitoring runs on the server it watches, so a dead server alerts no one; Alertmanager has no receiver
  yet (`shown-only`); there is no error tracker; CI reads the database repository at a feature branch
  (`FA-13-fixes-and-improvements`).
- **Revisit**: before going live: a receiver that reaches someone and an external uptime check. CI moves to `develop`
  once that branch is merged.

## Product

### Oro has no accounts

- **Today**: Oro trusts tokens from an account system that does not exist yet.
- **Revisit**: before the Oro launch (`ORO-LCH-001`), after the asymmetric tokens (`ORO-SEC-003`).

### Anyone can reach anyone in Oro

- **Today**: any Oro user can open a direct conversation with, or add to a group, any other.
- **Why**: Umoja's organizations already bound who meets whom; Oro was built on the same model.
- **Risk**: spam and harassment from the first day of a public app.
- **Revisit**: before the Oro launch (`ORO-SEC-013`).

### Fixed scope of features

- No moderation by admins, no threads, no edit history, no push, no group pictures.
- **Revisit**: moderation and replies for the Umoja launch if customers ask; push for the Oro launch; the rest after
  (`ORO-FEA-001` to `ORO-FEA-007`).
